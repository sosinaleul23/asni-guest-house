The Problem

Small guest houses run on paper and phone calls

Manual hotel management creates real operational pain in the Ethiopian hospitality sector.

Paper Registers
Room bookings, guest IDs, and check-in dates are written by hand. A single water spill or lost notebook means lost revenue and legal traceability.
No Online Presence
Walk-ins only. Travellers researching Jimma on Google have no way to see room availability, prices, or menu before arriving.
No Staff Roles
Everyone can see everything. There is no separation between owner, receptionist, and guest — a compliance and privacy problem.
The Opportunity
Jimma sits on a growing tourism corridor (Aba Jifar Palace, coffee farms, university visitors). A small, focused web app can triple booking visibility at near-zero infrastructure cost.
Project Objectives

What this app is built to solve

Digitize the Booking Flow
Replace paper registers with a searchable, filterable bookings table backed by a real database.
Role-Based Access
Distinct experiences for Admin, Receptionist, and Guest — enforced on the frontend and validated on the backend.
Full CRUD on All Entities
Rooms, Users, Bookings, Menu Items, Orders, Tables, and Banners — create, read, update, delete.
Zero-Cost Hosting
Deployable on free tiers of Vercel (frontend) and Cloudflare (edge API + D1 database).
Framework-Free Frontend
Build a full SPA-like experience using only HTML, CSS custom properties, and vanilla JavaScript — no React, no Vue.
Production-Ready UX
Toast notifications, glassmorphism, responsive layout, live charts, and keyboard-accessible modals.

System Architecture

Three-tier, edge-first architecture

Client Browser
index.html · style.css · app.js
Cloudflare Worker
POST /api/query · JSON
Cloudflare D1
SQLite at the edge
Request Lifecycle
  • User clicks a button in the SPA
  • JS calls apiQuery(sql, params)
  • fetch() POSTs JSON to the Worker URL
  • Worker prepares & binds the SQL statement
  • D1 executes and returns rows
  • JS re-renders only the affected views
Why This Architecture?
  • No server to manage — Cloudflare runs it
  • Global low latency — data served near the user
  • Parameterized SQL — prevents SQL injection
  • Offline fallback — app caches data in localStorage if the API is down
  • Free tier friendly — 100k requests/day on Workers

Backend API

One endpoint, all the power

A single POST /api/query endpoint handles every CRUD operation with parameterized SQL.

// Cloudflare Worker — request handler
export default {
  async fetch(request, env) {
    // 1. CORS preflight
    if (request.method === "OPTIONS") { ... }

    // 2. Health check
    if (url.pathname === "/api/health") { ... }

    // 3. SQL execution endpoint
    const { sql, params } = await request.json();
    const stmt = env.DB.prepare(sql);
    const boundStmt = params.length
      ? stmt.bind(...params) : stmt;

    const result = sql.toUpperCase().startsWith("SELECT")
      ? await boundStmt.all()
      : await boundStmt.run();

    return Response.json({
      success: true,
      results: result.results
    });
  }
};
Security: Parameterized SQL
Instead of concatenating user input into SQL strings, we use bound parameters. db.prepare("... WHERE id = ?").bind(id) means D1 sends the SQL template and values separately — SQL injection is impossible by design.
CORS Handled
Proper Access-Control-Allow-Origin headers let the Vercel frontend call the Worker from a different domain.
Edge Execution
The Worker runs in Cloudflare's V8 isolates — cold starts under 5ms, no container to boot, no region to choose. It scales to zero when idle.

Frontend · Design Philosophy

Five principles that shaped every screen

Clarity
Information is hierarchically organised. KPI cards first, then charts, then tables.
Feedback

Role Awareness
The UI visibly changes colour and layout based on the currently active role.
Mobile-First
Every layout starts from the smallest viewport and expands. No horizontal page scroll.
Performance
Zero frameworks, zero bundlers. Three files, cached forever, loaded in under 200ms.
The core belief
A well-designed admin UI is not decoration — it is operational efficiency. A receptionist who can check in a guest in 12 seconds instead of 90 saves the guest house real money.
Frontend · Layout Architecture

A fixed shell with a single scroll region

The most common CSS bug in admin dashboards is page-level overflow. This layout prevents it entirely.

App Shell
The <body> is a flex column at 100dvh (dynamic viewport height) — the header is fixed, everything else stretches to fill.
Body Row
A flex row containing sidebar (fixed 15rem) and main (flex: 1). min-height: 0 on both is critical — it is the secret that stops flexbox children from overflowing.
Only Main Scrolls
overflow-y: auto lives on .app-main only. The sidebar has its own scroll region. The page itself never scrolls — this eliminates the classic double-scrollbar bug.
/* style.css — the fixed shell */
.app-shell {
  display: flex;
  flex-direction: column;
  height: 100dvh;
  overflow: hidden;
}

.app-body {
  flex: 1;
  display: flex;
  min-height: 0;      /* the critical fix */
  overflow: hidden;
}

.app-sidebar {
  width: 15rem;
  flex-shrink: 0;
  overflow-y: auto;
}

.app-main {
  flex: 1;
  min-width: 0;
  overflow-y: auto;
  overflow-x: hidden;
}

Frontend · State Management

Single source of truth, one-way data flow

No Redux, no Context — just a plain object and a disciplined rendering pipeline.

// app.js — the entire client state
let db = {
  rooms: [], users: [], bookings: [],
  restaurant_tables: [], menu_items: [],
  orders: [], ad_banners: []
};

let currentRole = 'Admin';
let activeCart  = [];

function renderAll() {
  renderDashboard();
  renderRooms();
  renderUsers();
  renderBookings();
  renderRestaurant();
  renderTables();
  renderReports();
  renderBanners();
  renderSchema();

async function handleRoomSubmit(e) {
  e.preventDefault();
  await dbInsert('rooms', payload);
  await reload();
  renderAll();
}
The Flow
  • User clicks a button
  • Handler builds a payload
  • dbInsert/dbUpdate/dbDelete calls the API
  • reload() fetches fresh data from D1
  • renderAll() repaints every view
  • User sees the change with a success toast
Offline Fallback
If the API is unreachable, the same state object is populated from localStorage. Every mutation also writes back to localStorage. The app still works offline.
Why this works
Predictable, easy to debug — the state is always visible from DevTools, and every render is idempotent (safe to call any number of times).
Frontend · Interactive Components

Building a component library without a framework

Modals
One shared .modal class drives 9 different forms. Open with a dynamic title, close with click-outside, ESC, or an X button.
Cart
Adding the same item increments quantity instead of duplicating. Submission serializes to JSON for the items_json column.
Toast System
Every CRUD action produces a bottom-right toast. Success = green, error = red. Auto-dismiss in 3.2s.
Live Charts
Chart.js draws revenue trends and room categories on canvas. Instances are destroyed before re-creating to prevent memory leaks.
Data Tables
Responsive tables hide non-critical columns below md and lg. Every row has icon-only Edit/Delete buttons.
Receipts
A dedicated print stylesheet transforms the modal into a clean, black-on-white invoice when Ctrl+P is pressed.
CSV Export
Financial reports are computed live, then serialized to CSV and downloaded via a Blob URL — no server round-trip.
Accessibility
Tab order follows visual order. Real button tags. ESC closes any modal. Focus rings are preserved.
The pattern
Every "component" is a self-contained function that builds DOM once and then only replaces innerHTML on re-render.
Frontend · Responsive Design

Mobile-first, tested to 320px

Every layout decision starts small and expands. Breakpoints at 480, 640, 768, and 1024px.

Mobile (≤ 480px)
  • Sidebar becomes an overlay drawer
  • KPI cards stack 2-per-row
  • Tables hide low-priority columns
  • Modals become full-height sheets
  • Charts shrink to 13rem height
Tablet (≤ 768px)
  • Sidebar toggles via hamburger
  • Grid collapses to 2 columns
  • Numeric tables stay compact
  • Modals cap at 92vh with scroll
  • Tap targets ≥ 44px
Desktop (≥ 1024px)
  • Full 15rem fixed sidebar
  • 4-column KPI grid
  • Wide 3-column dashboard
  • Hover states on all rows
  • Charts at 16rem height
The min-width: 0 trick
The single most important CSS rule in the layout. Without it, flex children refuse to shrink below their content size — a 900px table inside a 500px column pushes the whole page wide.
Fluid typography
Headings use clamp() so they scale smoothly with viewport width. No awkward jumps between breakpoints.

Theming & Localisation

Two cross-cutting features that make the app usable by every guest, in every condition — day or night, in English or Amharic.

Frontend · Theming

One attribute, two complete themes

A dark-first design with a fully-crafted light variant — togglable in one click, persisted across sessions.

The mechanism
Every themeable value lives in a CSS custom property. The theme is switched by setting data-theme="light" (or "dark") on <html> — one attribute flip.
Semantic variables
No component references raw colours. They only reference tokens like --bg, --panel, --border, --text, --muted.
Persistence & sync
Choice saved to localStorage under asni_theme_v1. On every boot, applyTheme() reads it back and re-applies before paint.
/* Dark — the default */
:root {
  --bg:         #05080f;
  --panel:      rgba(30,41,59,0.7);
  --border:     rgba(148,163,184,0.14);
  --text:       #e2e8f0;
  --muted:      #94a3b8;
}

/* Light — only overrides what changes */
[data-theme="light"] {
  --bg:         #f1f5f9;
  --panel:      rgba(255,255,255,0.85);
  --border:     rgba(15,23,42,0.10);
  --text:       #334155;
  --muted:      #64748b;
}

/* Toggle in JS */
function applyTheme(theme) {
  document.documentElement.setAttribute('data-theme', theme);
  localStorage.setItem('asni_theme_v1', theme);
}
Why this matters for UX
Reception staff work day and night. A bright light theme is comfortable for daytime check-ins; a dark theme reduces eye strain during night shifts.
Frontend · Localisation

Full Amharic (አማርኛ) translation, zero dependencies

A hand-written i18n system in ~80 lines of JavaScript — no i18next, no react-intl, no build step.

Dictionary structure
A single JS object T with two keys: T.en and T.am. Each holds hundreds of keys covering every visible string.
Automatic application
Every static label carries a data-i18n="key" attribute. applyLang() walks the DOM once and swaps textContent for each matching key.
Safe fallback
t(key) falls back to English if a translation is missing. The UI never shows a raw key like "btn_add_room".
Font swap on demand
When lang="am", the body gets a .lang-am class that switches the font stack to Noto Sans Ethiopic — the correct typeface for the Ge'ez script.
/* Dictionary */
const T = {
  en: { nav_rooms: 'Rooms', status_Available: 'Available' },
  am: { nav_rooms: 'ክፍሎች', status_Available: 'ነፃ' }
};

/* Lookup with fallback */
function t(key) {
  return (T[currentLang] && T[currentLang][key])
      ||  T.en[key] || key;
}

/* One-call application to the whole DOM */
function applyLang(lang) {
  currentLang = lang;
  localStorage.setItem('asni_lang_v1', lang);
  document.documentElement.setAttribute('lang', lang);
  document.body.classList.toggle('lang-am', lang === 'am');

  document.querySelectorAll('[data-i18n]').forEach(el => {
    el.textContent = t(el.dataset.i18n);
  });
}
The critical DB decision
Database values stay English-only. When a room's status is 'Available' in SQLite, it stays 'Available' — because the CHECK constraint requires exact English strings. Translation happens at render time.
What gets translated
All navigation, page titles, subtitles, table headers, form labels, button text, modal titles, toast notifications, status pills, room types, zones, categories, roles, receipt templates, and chart legends.

Frontend · Architecture Trade-offs

Why hand-written i18n beats a library here

A deliberate engineering decision — not a shortcut — for a project at this scale.

~80 lines total
The entire i18n layer fits in a single function plus a constant object. i18next would require ~35KB plus a plugin and build config.
No XSS surface
Translations live in a JS object and are set via textContent (never innerHTML), so malicious strings cannot inject markup.
Total control over fallbacks
Missing key → English fallback → key string. That three-tier fallback is written explicitly.
Separation of concerns
The database stores canonical English values. The UI is the only layer that translates. The same D1 database could serve a French frontend tomorrow.
Zero runtime overhead
No network request for locale bundles. Language switching is instantaneous — a synchronous DOM walk.
Learning value
Writing i18n by hand forces you to understand the real problem: dynamic text is a first-class concern.
Summary
Theming and localisation are not just features — they are architecture decisions that prove the codebase is well-factored.

Security & Data Integrity

Defense in depth

SQL Injection Prevention
Every query uses parameterized statements. The SQL template and the data travel separately through the Worker to D1.
Output Escaping
Every string inserted into the DOM is passed through escapeHtml() before interpolation. This blocks stored XSS.
CHECK Constraints
Roles, room types, statuses, zones, and categories are all validated at the SQLite layer. Bad data is rejected at the source.
Referential Integrity
Bookings reference rooms.id via foreign key with ON DELETE CASCADE. Deleting a room safely cleans up its bookings.
Frontend-side role enforcement
Roles hide UI elements and disable buttons. This is presentation-level security — it improves UX but is not a substitute for real authentication.

Challenges & Solutions

What was hard, and how it was solved

Challenge 1 — Page overflow
Symptom: entire page scrolled horizontally when a wide table was present. Root cause: flexbox children default to min-width: auto. Fix: min-width: 0 on every flex parent + overflow-x: auto on a table-wrap ancestor.
Challenge 2 — Chart memory leaks
Symptom: page became sluggish after 20+ tab switches. Root cause: Chart.js keeps a reference to every canvas. Fix: track each instance in a module-level variable and call .destroy() before every re-render.
Challenge 3 — Role switching breaks the UI
Symptom: switching to Guest while on SQL Console left the user stranded. Fix: if the active tab becomes hidden, programmatically click the Dashboard tab.
Challenge 4 — Offline resilience
Symptom: brief API unreachability showed blank tables. Fix: on boot, try D1 first; on failure, transparently load the last cached state from localStorage.
Challenge 5 — Theming without duplication
Symptom: every component would need two full CSS blocks. Fix: introduced CSS custom properties. Light theme became a ~20-line override block instead of a full stylesheet.
Challenge 6 — Localising DB content
Symptom: statuses come from the DB locked by CHECK constraints. Fix: kept canonical values English-only and built a translation layer that maps DB values to display strings for every locale.
